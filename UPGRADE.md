# Обновление до 0.2.0

## Типы полей в окне заполнения (08.09.2026)

Для `date` используется календарь, для `datetime` — календарь с временем и секундами. Множественные даты представлены отдельными элементами с добавлением и удалением. `FillController` преобразует ISO-значения этих элементов в формат культуры портала через `Date::getFormat()` / `DateTime::getFormat()`, а при загрузке выполняет обратное преобразование. Часовой пояс применяется штатным обработчиком UF при сохранении; браузер не переводит выбранное время в UTC. Невозможные даты отклоняются.

Исправлены потеря числового нуля при построении формы и ошибочная трактовка массива строк `['0']` как пустого поля. Числовые строки, включая ведущие нули, остаются строками. Остальные ограничения строковых UF, заданные в CRM, продолжают действовать.

Обновите `lib/FillController.php`, `lib/RuleEngine.php`, `install/js/derykams.fieldaudit/runtime.js` и `runtime.css`. Откройте настройки модуля для копирования JS/CSS и перезагрузите карточку/слайдер. Закройте ранее открытые окна заполнения.

Источники: локальное ядро, `main/lib/userfield/types/datetype.php`, `datetimetype.php`, `stringtype.php`, `main/lib/type/date.php`, `datetime.php`. Проверены синтаксис изменённых PHP/JS, преобразование дат и времени (включая множественные значения, другой формат культуры и ошибочные даты), строки `0`, `123`, `00123`, длинные цифровые строки и пустые файловые значения. Элементы ввода и добавление/удаление дат проверены в Node с заглушкой DOM. Это изолированные проверки; портал и Chromium не запускались.

Для этой правки достаточно обновить `/local/modules/derykams.fieldaudit/lib/FillController.php` и повторить открытие окна.

Проверены синтаксис контроллера и связанных PHP-файлов, синтаксис runtime.js. Изолированная проверка с настоящим `ControllerBuilder` из локального ядра и заглушками окружения подтвердила автозагрузку класса, доступность `load/save/trace`, имена параметров и фильтры Authentication/POST/CSRF. Полный запуск на портале и браузерные проверки не выполнялись. Предыдущие пометки «проверки не запускались» относятся к предыдущим изменениям.

## Дополнительная диагностика файлов и форматов удаления (08.09.2026)

Предыдущая правка охватывала только `<controlId>_deleted`. Добавлена обработка `UF_CRM_..._del`: ID/списка ID и старых флагов `Y`, с проверкой принадлежности старым файлам сделки. Старые значения файлов теперь читаются отдельным штатным вызовом `GetUserFields` с ID сделки. Представление хранимого файла отделено от upload-операции; поддержаны списки ID, сериализованные списки и массивы описания файла с `ID`. Это закрывает обнаруженные пропуски, но конкретный источник `previousCount: 0` на портале нельзя установить по прежнему журналу без исходных значений.

Подробный лог включён константой `Diagnostics::FIELD_DEBUG` в `lib/Diagnostics.php`. Для отключения установите `public const FIELD_DEBUG = false;` на сервере. Значения собираются только для полей включённых правил и хранятся в сессии пользователя 10 минут (последние 8 запросов, максимум 200 событий на запрос). Строки ограничены 500 символами, массивы — 30 элементами. Файлы не читаются: выводятся ID, имена/размеры ранее сохранённых файлов, метаданные загрузки и признаки удаления; временные пути скрыты. Краткий серверный журнал работает независимо от этой константы.

Runtime получает `X-Derykams-FieldAudit-Debug` даже при разрешённом сохранении и запрашивает подробности через `FillController.trace`. Endpoint проверяет POST, sessid, текущего пользователя, срок записи и права чтения сделок. В консоли появятся:

- `[FieldAudit] server.file.database`: значение из списка CRM и значение из API пользовательских полей, включая тип PHP.
- `[FieldAudit] server.file.input`: присутствие поля в изменениях, исходное значение формы, `controlDeleted`, `legacyDeleted`, `acceptedDeleted`.
- `[FieldAudit] server.field.values`: значения до операции, предложенные и эффективные значения; `transition: filled|cleared|remains_filled|remains_empty`, ID/имена старых файлов. Это этап `before_save`, а не подтверждение записи.
- `[FieldAudit] server.condition.field`, `server.condition.group`, `server.rules.allow/block`: решения правил.
- `[FieldAudit] server.deal.saved`: событие успешного сохранения CRM. У каждой записи есть время сервера и общий `trace` для связи с запросом.

При ошибке загрузки подробностей появится `server.trace_error`. Записи доступны также через `BX.FieldAuditRuntime.getLog()` (последние 200 клиентских событий).

Перенесите на портал актуальные `FileState.php`, `DealState.php`, `Diagnostics.php`, `RuleHandler.php`, `FillController.php`, `include.php` и `install/js/derykams.fieldaudit/runtime.js`. Откройте настройки модуля для копирования JS и перезагрузите карточку, включая открытый слайдер. Старые окна заполнения закройте. Проверки и браузеры для этой правки не запускались.

## Исправление контроля удаления файлов (08.09.2026)

Обновите `include.php`, `lib/DealState.php`, `lib/RuleHandler.php`, `lib/FillController.php` и добавьте `lib/FileState.php`. Для этой правки JS не менялся. Закройте ранее открытое окно заполнения и повторите операцию: старые контексты окна не содержат отдельно переданных признаков удаления файлов.

Причина: `main.file.input` передаёт удаление через `<controlId>_deleted`, сохраняя прежние ID в UF. Ядро обрабатывает этот признак позже, при сохранении пользовательских полей. Ранее модуль сравнивал только значения UF, поэтому считал удаляемое поле неизменённым. Кроме того, непустой массив `old_id/del/error` воспринимался как заполненное значение.

Теперь файловые значения нормализуются отдельно: учитываются оставшиеся файлы, удаление последнего файла и замена новой загрузкой. Ноль, пустой список и операция удаления без новой загрузки дают пустое состояние. Запросы удаления проверяются по регистрации файлов штатного контрола. При оценке условий не выполняются операции над физическими файлами; отмена pop-up не сохраняет удаление. Подтверждённые операции из исходного запроса сохраняются в контексте окна для повторного сохранения через CRM.

В pop-up заполненность рассчитывается тем же способом, поэтому помеченный на удаление файл больше не считается выполненным требованием. Добавление файла в множественное поле учитывает исходные удаления и оставшиеся файлы. Для диагностики добавлено событие `file.state`: `deletionRequested`, `registeredDeletions`, `deleteOperations`, `previousCount`, `currentCount`. При удалении последнего файла ожидается `currentCount: 0`, затем `condition.field` с `previousFilled: true`, `currentFilled: false`, `changed: true`.

Правило с одним файловым полем и `changed_to_empty` менять не нужно. В правиле с двумя полями и `fillMode: any` удаление одного поля при заполненном втором по-прежнему разрешено: требование «хотя бы одно заполнено» уже выполнено. Для обязательного восстановления каждого очищенного поля задайте отдельные правила с одним полем в действии.

Источники: локальное ядро `main/lib/ui/fileinpututility.php` (`getUserFieldCid`, `checkFiles`, `checkDeletedFiles`), `main/lib/userfield/types/filetype.php` (`onBeforeSave`), `main/classes/general/usertypemanager.php` (`EditFormAddFields`, `Update`), `crm/classes/general/crm_deal.php` (порядок событий и сохранения UF). Исходники ядра не изменялись. Тесты и браузеры для этой правки не запускались; работа на портале пока не подтверждена.

## Применение на портале

1. Обновите файлы модуля в `/local/modules/derykams.fieldaudit/`, включая новые классы в `lib/`, `include.php` и содержимое `install/js/derykams.fieldaudit/`.
2. Откройте страницу настроек модуля пользователем с правом W. Она обновит JS/CSS в `/bitrix/js/derykams.fieldaudit/` и зарегистрирует обработчик подключения окна `OnProlog`. Обработчики CRM регистрируются установщиком. Если веб-сервер не может записать файлы, страница покажет сообщение об ошибке.

Удалять и устанавливать модуль заново не требуется.

## Сценарий «А и Б пусты → переход на С → заполнить одно или оба»

В одном правиле задайте:

- Группа условий с логикой **И**.
- Поле А: **На заполнение → Не заполнено**.
- Поле Б: **На заполнение → Не заполнено**.
- Дополнительное условие стадии: **Сделка переходит на стадию → С**.
- Действие: **Окно заполнения**.
- Условие продолжения: **Заполнить хотя бы одно из выбранных полей**.
- Поля окна: автоматический выбор полей с условием «Не заполнено» либо явно А и Б.

Сохраните настройки. Если оба поля пусты, попытка перехода отклоняется и открывается окно. После заполнения одного поля или обоих кнопка «Сохранить и продолжить» сохраняет значения и исходное изменение стадии штатным методом CRM.

Режим **Заполнить все выбранные поля** требует заполнения всех полей окна. Его требования проверяются на сервере при отправке формы.

Удаление всех правил и сохранение пустого списка отключает контроль. Демоправила больше не восстанавливаются автоматически.

## Реализация и ограничения

- Поля и стадии проверяются совместно. Режим «переходит» сравнивает предыдущую и новую стадии; режим «находится» проверяет новую/текущую стадию без требования перехода.
- Реальное окно подключается отдельно от симулятора. Оно реагирует на заголовок ответа BX.ajax `X-Derykams-FieldAudit` либо маркер отклонённой операции в тексте ответа; стандартное уведомление CRM также может отображаться.
- Контекст операции хранится в сессии 15 минут. Права пользователя, sessid, изменение правил и параллельные изменения сделки проверяются повторно при сохранении.
- Окно поддерживает строковые, числовые, файловые поля, даты, Да/Нет и списки. Для других типов необходимо заполнение в карточке сделки. Для множественного файлового поля можно добавить один файл за отправку.
- После успешного сохранения страница перезагружается для отображения актуальной стадии и значений.
- Настройки фильтров аудита сохраняются при редактировании списка правил.

Источники реализации: исходники модуля и локальная копия ядра Битрикс — обработчики совместимых событий сделки, BX.ajax, PopupWindow и DealCategory.

До остановки проверок пользователем прошли 43 серверных контрактных утверждения. Браузерная проверка не завершена; Chromium для проверок запрещён пользователем. Прогон на реальном портале не проводился.

## Исправление отсутствующего окна и диагностика (07.09.2026)

В локальной копии ядра `modules/crm/install/components/bitrix/crm.deal.list/list.ajax.php`, ветка `SAVE_PROGRESS`, при отказе `CCrmDeal::Update()` возвращает прежний `VALUE`, но не включает `LAST_ERROR`/`RESULT_MESSAGE` в ответ. Маркер `[DERYKAMS_FIELDAUDIT:…]` терялся, поэтому подписка на `onAjaxSuccess` не открывала окно. Стандартное окно из примера CRM открывается по `CHECK_ERRORS`; отказ обработчика событий сам по себе не создаёт эти ошибки обязательных полей.

Теперь `Integration::publishChallenge()` передаёт токен также через HTTP-заголовок. Runtime читает его из `config.xhr` на `onAjaxSuccess` и `onAjaxFailure`, сохраняет поддержку текстового маркера и не открывает одно окно дважды. Для старого progressbar восстанавливается индикатор прежней стадии. Ядро CRM не изменяется.

Логи включены автоматически:

- Сервер: `/upload/derykams.fieldaudit.log` относительно корня портала. Новые записи — JSON, по одной на строку. `rules.begin` содержит стадии; `rule.stage`/`rule.skip` объясняют отбор; `condition.field` содержит ID поля, оператор, заполненность до/после и результат; `condition.group` — результат И/ИЛИ. При досрочном завершении И указан `shortCircuitAt`, остальные условия не вычислялись.
- `rule.fill_requirement` показывает режим `any/all`, поля и выполнение требования. `rules.block` и `challenge.header_sent` подтверждают отказ и подготовку сигнала. `popup.load.begin/ready/error`, `popup.save.begin/done/error` описывают обработку запросов окна.
- Консоль страницы CRM: фильтр `[FieldAudit]`. Ожидаемая цепочка: `runtime.ready` → `response.received` с `headerSignals: 1` → `challenge.open` → `request.success` → `popup.build` → `popup.shown`. Для старого progressbar дополнительно видны `stage.request` и `stage.restored`.
- Последние 200 клиентских записей доступны через `BX.FieldAuditRuntime.getLog()`. Серверные и клиентские записи связаны первыми восемью символами токена (`challenge`). Значения CRM-полей и полные токены в диагностические записи не выводятся.

Для приведённого правила при двух пустых полях и переходе на `UC_S73P0S` ожидаются два `condition.field` с `result: true`, группа И с `result: true`, требование `mode: any`, `satisfied: false`, затем `rules.block`. Кнопка «Отмена» закрывает окно без запроса сохранения. Заполнение одного поля или обоих разрешает сохранение полей вместе с исходной стадией.

Обновлять нужно PHP-файлы, `include.php` (автозагрузка нового `lib/Diagnostics.php`) и `runtime.js`; затем выполнить шаги применения выше. Эти исправления основаны на анализе исходников модуля и ядра. Тесты и браузеры для этого изменения не запускались; работа на портале не подтверждена.
